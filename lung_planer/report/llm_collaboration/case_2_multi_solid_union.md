# 案例 2：PL 原生多实体并集

## 用户提示词

我需要 PL 端还可以加速目前的多个 `Bronchus_plan` 肺段，应该怎么做呢，有哪些方法？

请先不要只根据 Python 接口或 ABI 给结论，先检查实际 RTL 数据通路和硬件限制，再提出方案。重点确认当前网格核是否保留肺段/实体标识、交点排序与内外判断方式、交点缓存深度、遍历栈深度、核配置和 ABI 版本等。

对多实体肺段，请按并集语义分析重叠区域和内部接口，不能简单拼接三角网格。可以评估通过实体标记、分组区间合并形成并集边界，并复用现有体积积分核等方向；但请明确区分“可行性”“预期收益”和“实测结果”，在未做 RTL/ABI 改造、仿真、重建和板测前，不要断言哪种方案最快，也不要把设计设想写成已验证功能。

请给出候选方法、各自需要的 RTL/ABI 改造、风险、验证步骤和预期收益；若证据不足，请明确说明。

## 模型回答与行动

检查 Verilog 后确认：当前网格核把交点统一排序，并按奇偶性判断单实体内外，没有保留肺段标识。

据此提出一个方向：通过实体标记、分组区间合并形成并集边界，并复用现有体积积分核。

## 自我纠错轨迹

- 模型先给出了「预处理并集可能最快」之类的建议，但承认当时只看了 Python 接口和 ABI，没有看 RTL，结论证据不足。
- 检查 `lung_ray_mesh_axi.v` 等源码后，修正了对硬件限制的判断。
- 明确各方案的实际速度尚未测量，不能断言哪种最快。

## 验证证据与结果

- 核查确认：单核配置、128 个交点缓存、128 层遍历栈，当时的 ABI 为 `0x00060000`。
- 当前阶段五 bitstream 与交付文件的哈希一致。
- 方案仍需 RTL/ABI 改造后做仿真、重建和板测，设计设想没有被当作已验证的功能。

## 可复用经验

- 提出性能建议之前，先查真实的数据通路和 RTL。
- 区分可行性、预期收益与实测结果。
- 对多实体几何，必须用并集语义处理重叠与内部接口，不能简单拼接三角网格。
